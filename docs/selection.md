## 1. StackReceipt：最贴近运维，但不宜轻易称新

**已有能力与剩余工作。** InferDoctor 已明确覆盖证据驱动诊断、第一故障层、UNKNOWN、最小下一探针、修复验证和回归门禁；因此“先诊断再复查”不能算我们的创新。K8sGPT 将分析器和 AI 用于 Kubernetes 扫描排障；HolmesGPT 已做多数据源事故调查和部署健康验证，也支持非 Kubernetes 基础设施。用户仍需为自己的具体栈提供故障样本、可重放输入和验收规则，这可以成为小范围交付，但不是这些项目做不到。

- 核心差异化假设：只支持 FastAPI→Ollama 调用链的连接拒绝、错误模型名、超时，用同一探针给出前后检查收据。AI 只能提出原因候选，已观察事实单列。
- 有价值的难点：区分“服务能连上”与“模型实际能响应”；网络观测无法单独证明根因。探针必须有超时、范围和 UNKNOWN。
- 可复现使用案例：本地把模型名改成不存在的标签，保留真实 HTTP 状态；改正后重复原探针。属于实际本地故障实验，不是假设客户案例。
- 60 秒：10 秒看调用拓扑；15 秒注入错误模型名；15 秒展示原始证据和候选原因；20 秒修复重查、比较收据。
- 指标：每种故障的分类结果、未知比例、错误“修复成功”数；样本和分母固定。未做实验，暂无数值。
- 初学者边界：只做 3 类故障、只读检查；不自动执行修复命令、不诊断 CUDA/K8s/所有 RAG。
- 为什么不只是套壳：差异若成立，应由故障注入、探针语义、失败分类和前后验证证明；仅让 LLM 阅读日志不成立。
- 追问：① HTTP 200 为什么不等于模型健康？② 怎样证明是模型名错误而非网络错误？③ 修复前后探针输入不同还能比较吗？

## 2. ResumeLedger：恢复不是加一个 retry

**已有能力与剩余工作。** LangGraph 已提供持久执行、人机介入和状态；DBOS 用数据库提供持久工作流、队列、通知和恢复；Temporal 提供长流程编排、活动重试、信号和重放。检查点、人工审批、重试都不是新功能。可做的细分工作是把“审批后生成一个本地归档文件”这个业务的副作用语义和故障演练讲清楚。

- 核心差异化假设：每个文件产物附内容哈希与操作幂等键，界面指出崩溃发生在副作用之前/之后，恢复前核对收据。
- 难点：外部副作用成功但状态尚未提交的窗口。SQLite 事务并不能让外部系统自动获得 exactly-once；MVP 限本地文件原子替换且有幂等校验。
- 可复现案例：AI 建议工单归档文件名，人工批准；在文件写入后、状态提交前故意终止进程，再重启。
- 60 秒：看待审批→批准→注入崩溃→恢复→检查只有一个预期产物且收据吻合。
- 指标：固定崩溃窗口下的重复产物数、丢失产物数和恢复成功数。尚未实测。
- 可行性：只做顺序 3 步与一个允许的文件操作；通用 DAG、外部支付和分布式执行都砍掉。
- 非套壳依据：必须自己实现或解释幂等边界、原子性和故障测试；调用框架 resume API 不足以构成特色。
- 追问：① 副作用成功后进程挂了怎么办？② 幂等键碰撞/重复输入如何处理？③ 为什么不能保证任意外部 API exactly-once？

## 3. LineScope Quotes：选择的方向

**已有能力与剩余工作。** LangExtract 已有精确来源定位、结构化抽取、本地模型和交互展示；invoice2data 已支持发票模板、明细抽取、多后端和 AI 回退；AI Procurement Verification Agent 已做订单与发票的行级匹配、数量/价格差异和附加费用检查；Tender Evaluation Assistant 已把页引用、规则、人工纠正和价格排序结合起来。不能宣称“AI 抽取 + 引用 + 人工审核 + 金额校验”从未有人做过。

[Docling](https://github.com/docling-project/docling) 已提供多格式解析、PDF版面/表结构、OCR和本地运行；它说明应复用成熟解析层，而非把自行增加PDF上传当创新。本次选择把PDF留到后续。其余两个最接近仓库链接为 [AI Procurement Verification Agent](https://github.com/AnishaPaturi/AI-Procurement-Verification-Agent) 与 [Tender Evaluation Assistant](https://github.com/tender-eval-ai/tender-evaluation-assistant)；二者为公开代码对标，许可和实际功能完整性仍需分别核查，不仅凭公开仓库就认定可以复制代码。

本项目可尝试的更小交付是：**一个开发者能够嵌入自己应用的、按当前明细范围验证字段的本地核验流程**。特征由 `OUTSIDE_ITEM_SCOPE`、`PARTIAL_NUMBER`、`TOTAL_MISMATCH`、`COVERAGE_UNCONFIRMED` 等可重现规则及导出格式来说明。竞品是否有等价细节需继续看代码，不以 README 没写作结论。

- 核心差异化：值与引用一致仍不够；引用必须定位在当前明细范围内、对应原文完整数值；总额引用不能偷用明细金额。未确认覆盖和简单计价时不能输出限定检查通过。
- 难点：重复数字和错误行引用、部分数值匹配、Decimal 与逐行舍入、保持原文和模型候选供复核。**存在性验证不是语义蕴含证明**；模型提供的 scope 也可能错误。
- 可复现案例：内置自制设备报价，3×1200 + 2×450 = 4500；把原文总额和候选都改成 4200，仍能定位少计 300；把 A2 的数量引用放进 A1，尽管同页有该数字也拒绝。
- 真实应用场景：采购助理/实施人员接收小型设备报价后先做复核。本次只有模拟材料和本地验证，**没有真实用户使用记录或节省工时证明**。
- 60 秒：20 秒展示串行拒绝；20 秒展示原文总额少计；20 秒展示正常报价待复核、人工确认后另存版本并导出。参见演示脚本。
- 指标：规则用例结果、已知矛盾的误通过数、引用可解析比例；真正的模型字段正确率必须用独立标注文本另外评估。没有实测的指标不填数字。
- 初学者可行性：只做文本、20 条以内、人民币、简单行金额；先把核验层跑通，最后接本地 AI。PDF/OCR、税费、供应商推荐和多文档匹配延后。
- 非套壳依据：LLM 只提候选，不决定通过；关键结果来自可离线重放的证据约束与业务计算。即便替换模型，核验规则、失败样本、版本与审阅流程仍存在。
- 追问：① 数字在原文中为什么仍可能错？② 少抽一整行、总额又恰好对上时怎么处理？③ 人工修正为什么不能覆盖原始记录？

## 4. VersionGate：不做另一个评测框架

**已有能力与剩余工作。** promptfoo 已支持模型/提示词对比、断言、CI 和红队测试；DeepEval 已支持多类应用、Agent 轨迹与指标；Ragas 已提供评估指标和测试集生成。另有 InferDoctor 的 RAG 前后回归，以及版本感知 RAG 的研究，不能把“文档版本 + 回归”说成全新方向。

- 差异化假设：专注客服手册发布前，用旧新条款的精确文本范围解释“这条答案依赖的依据已经失效”，保留未受影响用例的证据；作为现有评测工具的输入/报告层。
- 难点：文档排版变化不等于语义变化；diff 不能证明因果关系。先做标题/段落稳定 ID 与手工维护题目→依据映射，AI 仅建议关联。
- 案例：模拟“7 天退货”改成“15 天”，锁定两个文档版本，让旧答案的引用失效；未涉及退货的题保留。
- 60 秒：改一条手册→查看受影响的 3 题→展示旧引用和新依据→重跑对比。
- 指标：人工标注受影响题集上的召回率/精确率、旧版引用误通过数、实际模型调用次数。尚无实测。
- 可行性：只处理 Markdown 手册和固定 20 题；不用向量库也能先验证版本契约，后续再接检索。
- 非套壳依据：必须实现版本锁定、依据失效解释和可重复评测；仅调用 LLM 给答案打分不成立。
- 追问：① 格式改动如何避免误报？② 相关条款变化一定导致答案错误吗？③ 怎么避免用新答案或标签泄漏给被测系统？

## 5. ShareTrace：脱敏还要保留排障价值

**已有能力与剩余工作。** Presidio 提供敏感信息检测、识别器与匿名化管线；scrubadub 通过检测器清洗文本；OpenPipe 的 LLM 脱敏已支持标记、删除、假值替换和一致替换。因此“同一个姓名替换成同一个名字”也不是创新。

- 差异化假设：只接收应用 JSONL 日志，按字段策略保留状态码、错误类别和跨行请求关系，提供脱敏差异及“未验证区域”清单；让交接者能够核对排障信息是否仍可用。
- 难点：实体归一与关联保留可能反向增加可识别性；密钥变体、异常栈、自由文本都有漏检风险。MVP 不把原文发云端，不承诺自动达到发布安全。
- 案例：自制多行请求日志，包含邮箱、Bearer token、嵌套路径和共同 request_id；脱敏后仍能还原 500 的调用链，并检查已植入的秘密哨兵。
- 60 秒：看含假密钥的日志→本地检测→对比前后→同一请求链仍可追踪→看到未识别区域待复核。
- 指标：固定植入哨兵检出/遗漏数、错误删除数、请求链可重建数。都不是现实世界零泄漏证明。
- 可行性：20 种明确格式以内、结构字段为主；中文姓名全覆盖、各种文档和自动公开分享都延后。
- 非套壳依据：重点是输入输出契约、字段策略、可重复泄漏测试和排障可用性测试；只把文本交给模型改写没有特色。
- 追问：① 为什么稳定匿名 ID 仍有隐私风险？② 如何测试编码后的密钥？③ 脱敏后重放报错不同，怎么判断失真？

## 四类面试官的视角

这些是预期讨论点，不能保证面试官一定愿意点开或录用。首页 GIF、可运行命令和反例结果，比“企业级、多 Agent、智能中台”等词更有说服力。

| 项目 | AI 应用开发：快速兴趣 / 深挖 | Python 后端：可评估的工程点 | AI 实施运维：交付与排障 | FDE：问题转为约束与验收 |
|---|---|---|---|---|
| StackReceipt | AI 原因候选与观测事实分开，拒绝过度归因 | HTTP 超时、错误分类、探针契约 | 固定栈复现与修复复查；无自动修复越权 | 将客户“不能用”拆成可验证层，缩小调查范围 |
| ResumeLedger | 观察 Agent 恢复后的副作用，而非聊天记录 | SQLite 事务、幂等键、原子文件与崩溃测试 | 重启恢复、状态迁移与证据保留 | 选择可控业务边界，明确 exactly-once 的限制 |
| LineScope Quotes | 同页错误证据被拒；结构合法不等于事实可靠 | Pydantic、Decimal、版本不可覆盖、API 错误边界 | 模型不可用时有明确错误；离线重放与数据库恢复 | 把模糊“自动审报价”收缩为可解释复核，显式承认覆盖/语义需人工 |
| VersionGate | 文档升级为何破坏答案；模型/检索/版本分层 | 哈希、稳定 ID、差异、确定性断言与 CI | 升级前验收、回归与回滚依据 | 界定“哪些题因哪些条款变化必须复测”，而非评估所有问题 |
| ShareTrace | AI 检测与规则检测如何互补，避免错误保证 | 流式 JSONL、schema、替换一致性、边界测试 | 可分享的排障包及仍可定位的调用链 | 在可用性与泄漏风险间制定可解释的人工审查流程 |

每个项目都应留下开发失败记录、自动测试、安装部署、一次故意制造故障与恢复。生成代码不能代替本人理解；不懂的实现不写成个人掌握。

## 加权评分及依据

各维度 0–10 分，综合分 = 创新×2.5 + 面试×2.5 + 实用×2 + 可行×2 + 成长×1；满分 100。需求未经过访谈，实用和成长分有明显不确定性，约 ±5 综合分的排序波动是可能的。

| 项目 | 创新 25% | 面试 25% | 实用 20% | 可行 20% | 成长 10% | 综合 |
|---|---:|---:|---:|---:|---:|---:|
| LineScope Quotes | 7.5 | 8.5 | 7.5 | 8.5 | 7.0 | **79.00** |
| VersionGate | 7.0 | 8.5 | 8.0 | 7.0 | 7.0 | **75.75** |
| ShareTrace | 6.5 | 7.5 | 8.0 | 7.0 | 6.5 | **71.50** |
| ResumeLedger | 6.5 | 8.0 | 7.5 | 5.5 | 6.5 | **68.75** |
| StackReceipt | 5.0 | 8.0 | 8.0 | 7.0 | 6.0 | **68.50** |

- **LineScope**：反例肉眼能理解，Decimal、证据范围和不可覆盖修订容易用单元测试证明，范围可压到纯文本；同类多，所以创新只给 7.5。没有采购用户和真实扫描数据，实用不给高满分。
- **VersionGate**：与 AI 岗最直接，能讲回归；变化映射、检索与模型误差会混在一起，初学者 20 天内很容易解释不清，降低可行性。
- **ShareTrace**：交接需求合理，但检测很难证明充分，一致替换已有工具做到，安全维护负担降低创新与成长评分。
- **ResumeLedger**：故障演练很有技术讨论价值；核心问题已有成熟框架，持久恢复和副作用窗口超出初学者最稳妥范围。
- **StackReceipt**：职业方向匹配，但 InferDoctor 与 HolmesGPT 已非常接近，若只支持更少组件，很容易只是功能缩水，创新分最低。

## 决策与局限

选择英文名 **LineScope Quotes**，计划仓库名 **linescope-quotes**。本次精确仓库名搜索未返回同名，但这不是名称、商标或全球唯一性保证。

最值得证明的设计是：**自动输出只覆盖可证明的部分；正确 JSON、原文出现数字、甚至计算一致，都不能自动等于可以通过。** 这比继续添加框架更符合初级开发者能掌握的深度。局限是领域不直接等于运维，需通过本地部署、模型故障处理、导出重放和交付验收补足；文本范围是模型候选，完整性和语义仍需要人。若无法取得任何经授权的外部样本或访谈反馈，只应称为有明确应用假设的开源原型。

开发前完成标准：3 个可重现反例、API/规则/错误测试、原始记录保留、可离线重放、真实模型单独验证、安装文档、发布内容待用户审核。完整发布还需要干净克隆、Windows/Docker 与 GitHub CI 的实测，以及本人独立讲解验收。

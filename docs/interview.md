使用原则：这里只包装**已有证据支持的工作**。设计≠实现；自动测试通过≠本人掌握；Codex 生成≠本人独立编写。真实模型、Docker、跨平台和发布状态以 validation.md 为准。所有个人贡献先填写 personal-understanding.md，不能默认把整个仓库描述为独立开发。

## GitHub 项目介绍

LineScope Quotes 是面向小型设备报价的本地 AI 抽取与核验原型。AI 提出候选字段，Python 检查字段引用是否属于当前明细、是否截断数值，以及行金额和合计是否一致。缺失证据或未确认明细完整性时保留待复核状态。人工修订另存记录，导出的来源、候选、复核和报告可以在固定版本核验器上离线重放。

特色是可展示的错误边界，而不是自研模型。来源定位、采购比对和人工审阅都有成熟同类项目，本项目聚焦一个可理解、可复现的小范围交付。目前不支持 PDF/OCR、复杂计价或自动完整性证明。

英文简述：A local AI-assisted quotation review prototype with item-scoped evidence checks, Decimal arithmetic, explicit human review gates and replayable revision records. Built for explaining and reproducing errors, not inventing a new extraction model.

“这个项目处理设备报价抽取后的复核问题。大模型输出合法 JSON，并不代表数字属于正确的明细。我把来源定位限制到当前明细范围，再用 Decimal 复算金额。演示里，引用到同页另一行的数量会被拒绝，原文总额少计 300 元也会被发现。缺证据或尚未确认漏行时保留待复核，人工改动另存版本，可以离线重放。它的重点是可验证的工程流程，抽取能力来自本地开放模型。”

## 3 分钟技术讲解

**0:00–0:35，问题。** “报价单里，名字、数量、单价和金额经常被模型串到其他行。即使引用是真实原文，字段也可能不属于当前设备。只检查 JSON 格式和数字是否出现，覆盖不了这个错误。”展示 A1/A2 两行。

**0:35–1:05，对标与范围。** “LangExtract 已做来源定位，invoice2data 已做发票字段/明细，采购验证项目已做比对。我没有重做通用文档平台，选择了文本、小型设备、人民币简单计价，去做当前明细范围核验和可重放审阅。不是声称这些概念首创。”

**1:05–1:50，核心路径。** “Pydantic 限制结构与数值输入；模型只提出候选，人工确认字段不在模型 Schema 中。核验器先定位明细 scope，再只在该范围里查每个证据；必须唯一，数值要对应完整原文 token，不能截取 1200.00 的一部分。证据有效后才计算数量乘单价，按行舍入，再核对明细合计和总额。矛盾、未知和通过是三种状态。”展示相应错误码。

**1:50–2:25，交付与排障。** “FastAPI 提供抽取、核验、查询和新建修订；SQLite 保存原文、候选、人工复核与报告。修订不覆盖原记录。导出后使用相同版本核验器，不需要模型也能复算。模型不可用或输出错误时明确返回503/504，不会用模拟结果冒充。”只描述自己实际验证的部署方式。

**2:25–3:00，验证与局限。** “规则回归和模型质量分开。合成反例能证明当前规则处理了这些错误，不能代表真实报价准确率。引用存在不证明语义角色正确，明细 scope 本身也可能错；漏行、复杂税费和 OCR 不在自动保证内。下一步是独立标注未见版式，并比较模板抽取和模型抽取各自的适用范围。”补实际测试记录，不背未经实测的数字。

## 5 分钟完整演示

1. **0:00–0:40**：打开首页，说明文本范围和模拟样本，展示来源与两条明细，不先讲框架。
2. **0:40–1:30**：点真实 Ollama 抽取（若本机实测耗时太长，播放真实录屏或打开保存的真实结果并清楚标记），核对字段及证据；未确认时不能自动通过。
3. **1:30–2:15**：切换串行反例，证明数字在同页存在仍被拒绝；点击字段定位到来源。说明这里是受控反例，不是声称模型必定会这样出错。
4. **2:15–3:00**：切换原文合计错误，查看复算差额；尝试只把候选总额改对，说明它与来源不一致，不能通过。需要修订原文才建立新来源记录。
5. **3:00–3:45**：正常报价第一次待复核；亲自检查后填写复核理由，再保存新版本，展示父记录仍可读取。
6. **3:45–4:20**：导出 JSON，在终端执行 `python -m linescope.replay 文件.json`，展示 `identical: true`。强调它重放核验，不是重现模型输出。
7. **4:20–5:00**：停用/错误配置模型展示明确错误，打开验证记录和限制；说明本次实际跑过的测试与尚未完成的跨平台/发布验收。

## 技术难点与真实处理过程

仓库中已发生的工程定位示例：最初仅对引用字符串做数值解析，会有截断风险——把原文1200.00引用成1200，局部数值仍相等。实现增加了引用内 token 在**完整来源文本**中的边界对应，并补 `PARTIAL_NUMBER` 反例。另一个设计是禁止将行金额当成全单总额；即使数值出现，也因位置不符阻止通过。

上述是代码建设过程，可供本人复现实验和解释；不自动构成本人独立发现的经历。个人真实排障过程另行填写，不能背成自己亲历。

## 15 个深入问题与回答思路

| 问题 | 应解释的核心，而非背固定答案 |
|---|---|
| 1. 为什么 Pydantic/JSON Schema 不足以保证结果正确？ | 它约束结构与类型，不能证明来源、语义归属、明细完整性或算术关系。演示合法JSON里的错误引用。 |
| 2. 数字在原文中出现，为什么仍错？ | 同页另一行、同一行其他字段、旧版本或数值截断都可能误引。本项目自动约束当前scope和完整数值，语义角色仍需要复核。 |
| 3. scope 由模型给出，岂不是模型给自己作证？ | 是局限：代码能证明包含关系，不能证明scope是正确业务行。人工必须核对；后续使用确定性表格行/显式覆盖清单增强，不宣传已经解决。 |
| 4. 遇到相同金额出现两次怎么办？ | 不取第一处。要求更长唯一引用；同一明细内字段证据须唯一。精确匹配的保守性可能增加待复核。 |
| 5. 字段都正确、少一整行怎么办？ | 合计可能发现，有抵消或总额也不完整时发现不了；覆盖确认是人为责任，尚无自动完整性证明。报告这种失败比编造100%检出更合理。 |
| 6. 为什么 Decimal？舍入何时发生？ | float无法精确表示某些十进制金额。用字符串建Decimal，先逐行乘后ROUND_HALF_UP至分，再求和；其他舍入/税费规则不自动猜。 |
| 7. 为什么不是让另一个 LLM 检查？ | 第二模型也可能有相关错误，成本/复现性更复杂。确定性规则适合字符串与算术；语义问题仍可能需要模型/人工，不能用规则夸大能力。 |
| 8. BLOCKED 和 NEEDS_REVIEW 如何区分？ | 已发现可证明矛盾 vs 证据不足/歧义/未确认；矛盾优先。CHECKS_PASSED仅指限定规则，不是业务批准。 |
| 9. 人工把总额改对为什么还不能通过？ | 若原文仍写错，候选被改对也失去来源支持。要保留原错误并提供修订后原文建新记录；不能篡改证据迎合规则。 |
| 10. 什么能重放，什么不能？ | 原文、候选、复核、固定核验器可重算报告。temperature=0不保证不同硬件/版本模型输出完全一致；没有把重放包装为模型确定性。 |
| 11. SQLite 追加记录算不可篡改审计吗？ | 不算；API不提供覆盖，文件仍可被本机操作者改。哈希标识内容不证明签名/真实性；认证、签名、哈希链均未实现。 |
| 12. 模型超时/截断/输出非法时怎么办？ | 限本地地址和响应大小，固定超时和错误码，不静默回退到样本；重试前理解幂等和资源占用。本次阶段超时不是严格全请求SLA。 |
| 13. 如何证明比纯正则/模板更有用？ | 应在未见版式上公平比较字段准确率、漏行率、待复核数与观察耗时，保留全部失败。对固定模板正则可能更好，当前未证明模型总是必要。 |
| 14. 怎样防数据泄漏和提示注入？ | 本地推理、忽略数据目录、日志不写正文、服务端固定端点、Host/Origin检查、UI不用innerHTML、无执行工具；提示词不是免疫保证，恶意输入仍可能污染抽取。 |
| 15. 如果给你一个月和真实用户，先改什么？ | 先授权样本与需求访谈，分层标注和确定性行结构/覆盖清单；再决定原生文字PDF或计价规则，先扩大证据与测试，不先堆Agent/向量库。 |

## 后续可改进之处

优先补未见样本、模型基线和真实复核反馈；加强明细scope的独立确定依据；提供字段级编辑、差异查看；原生文字PDF保留页定位；版本固定与模型digest记录；再考虑受控计价规则和外部系统集成。性能优化须先测单文档真实瓶颈，不凭空承诺提升。
